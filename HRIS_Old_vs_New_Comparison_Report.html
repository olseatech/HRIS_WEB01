Section 1

Executive Summary

The HRIS Manila Council system was extended and hardened across a series of tracked changes. This report compares the Old HRIS (the system before this engagement) with the New HRIS (the system after adding the Leave Management module and enforcing server-side authorization). The comparison is drawn entirely from the project's own history: commit records, change-log documents, database migrations, application source, and User Acceptance Testing (UAT) screenshots.

Headline outcomes

AreaResult
New capabilityA full Leave Management module (CS Form No. 6 applications, Employee's Leave Card ledger, leave-type & holiday settings, PDF exports) — 32 files, ~3,120 lines added commit d0d8be0.
Security hardeningServer-side authorization enforced on leave endpoints, closing a privilege-escalation and IDOR exposure that would have let any employee tamper with leave credits and records commit b10c18b.
Earlier remediationPDS "self-edit" access control added across the employee data-sheet controllers, replacing UI-only restrictions with real backend ownership checks EMPLOYEE_PDS_EDIT_CHANGES.md.
Data-sheet qualityFive PDS enhancements (passport photo with validation, L&D hours override, part-time flag, government-ID date validation, GSIS ID) — additive and backward-compatible CHANGES_SUMMARY.md.
Build stateCompiles cleanly; deployable WAR (~92 MB), Java 11, Spring Boot 2.2.4 RUNTIME_ASSESSMENT_REPORT.md.
Bottom line. The New HRIS delivers a materially larger feature set and a stronger security posture than the Old HRIS. The most important improvement is the shift from "authenticated users are trusted" to "actions are authorized by role and record ownership." Residual risks remain and are listed as prioritized follow-ups in Sections 10 and 12 — none are blockers for the leave deployment.

Section 5

Added Module: Leave Management

The Leave Management module digitizes the Council's paper leave process (Civil Service Form No. 6) and the Employee's Leave Card ledger. Its design was derived from the Council's own procedure manual, the customized CS Form 6, and a real employee leave card LEAVE_MODULE_BLUEPRINT.md, then implemented as a new application package commit d0d8be0.

5.1 Workflow supported

  1. Record a leave application (CS Form 6) for an employee — office/department, position, salary snapshot, leave type, details, working days, inclusive dates, commutation.
  2. Certify leave credits — the system auto-computes VL/SL "Total Earned / Less this application / Balance" from the ledger.
  3. Recommend and Approve / Disapprove — with a special "disapproved due to exigency of the service — no deduction" path.
  4. Post approved leave to the Employee's Leave Card, deducting only from the matching ledger (VL or SL); several leave types deduct nothing.
  5. Export the completed CS Form 6 and the Leave Card as PDF.

5.2 Data model (migration 2026-leave-management.sql)

TablePurpose & key columns
leave_applicationOne row per CS Form 6. Filing/receipt dates, leave type & details, working days, inclusive dates, certification block (VL/SL earned/less/balance), recommendation, action (days with/without pay), disapproved_exigency flag, signatory names/titles. FK → employee.
leave_card_entryLedger rows. Entry type/date, period, particulars, vl_earned/vl_deducted, sl_earned/sl_deducted, remarks, optional FK → leave_application (links a posted entry back to its application).
leave_typeConfigurable leave types with legal basis and active flag; seeded on first boot.
holidayHoliday calendar (name, date, type, remarks); managed in System Settings.
Ledger logic. Monthly accrual posts 1.25 VL + 1.25 SL; running balances are computed per row. Only "V" entries deduct VL and "S" entries deduct SL — special-privilege, calamity, maternity and similar leaves are recorded without changing balances, matching the sample leave card. LeaveController.java · LeaveConstants.java

5.3 Components delivered

LayerArtifacts
Entities & repositoriesLeaveApplication, LeaveCardEntry, LeaveType, Holiday (+ Spring Data repositories)
ControllersLeaveController, HolidayController, LeaveTypeController
SeedingLeaveSettingsSeeder — seeds leave types on first boot
ReportsJasper templates CS-Form-6-Leave.jrxml, Leave-Card.jrxml
Views (Thymeleaf)employee/leave/employee-list-leave.html, employee-leave-record.html; settings pages for holiday & leave type

5.4 Access model within the module

Staff (HR/Admin) file, certify, approve and post leave. Employees have a read-only self-service view (/my-leaves): the templates gate every File/Submit/Delete/Add-Entry/Post-Accrual control behind th:if="${showMode != 'EMPLOYEE'}". As delivered, that read-only intent is now also enforced on the server (see Sections 8 and 10).

Section 8

Fixes Implemented

Each fix is shown as what was wrong → what changed, with a citation to the change record.

8.1 Leave module — server-side authorization commit b10c18b

Before: Every leave endpoint was gated only by "authenticated." The UI hid admin controls from employees, but the server did not enforce it, so any ROLE_EMPLOYEE could call the endpoints directly.

After: Admin/mutation endpoints are role-gated; the one dual-use PDF endpoint gets an ownership check.

// SecurityConfig — admin & mutation endpoints now require staff role
.antMatchers(LEAVE_ADMIN).hasAnyAuthority("ROLE_ADMIN", "ROLE_HR")
// LEAVE_ADMIN = /leaves, add/update/delete Leave Application & Card Entry,
//               /postLeaveAccrual, /holidays, /leave-types (+ save/delete)

// LeaveController.exportForm6Pdf — /leaveForm6Pdf/{id} own-record-or-staff guard
boolean isStaff = "ROLE_ADMIN".equals(t) || "ROLE_HR".equals(t);
if (!isStaff && !isOwnRecord) { response.sendError(SC_FORBIDDEN); return; }

8.2 PDS self-edit — backend ownership checks EMPLOYEE_PDS_EDIT_CHANGES.md

Before: "The backend had no access control on the save endpoints — any authenticated user could POST to them." Restrictions were JavaScript-only.

After: Ownership check added to EmployeeController and all 10 PDS sub-controllers; also prevents privilege escalation via userType tampering.

Employee actorObj = (Employee) request.getSession().getAttribute("actorObj");
boolean isAdmin = actorObj != null && "ROLE_ADMIN".equals(actorObj.getUserType());
boolean isOwnRecord = actorObj != null && actorObj.getId() == entity.getEmployee().getId();
if (!isAdmin && !isOwnRecord) { /* redirect: Access denied */ }
if (!isAdmin && isOwnRecord) employee.setUserType(old.getUserType()); // no self-promotion

8.3 PDS save validation bug commit e906631 · PDS_SELF_EDIT_BUG_FIX.md

Before: After enabling self-edit, employees hit "Mandatory fields marked in RED" because HR-only fields (employee no., assumption date, status, position, division) were validated as required though employees never fill them.

After: HR-only fields are locked read-only/disabled client-side and restored from the database on save, so employees can submit and HR-managed values are never nulled.

8.4 Clearance robustness commit 5cb1379

Null-safe PDF generation, a missing record ID on disapprove, and an addressTo binding issue were corrected in clearance processing.

Section 9

Vulnerability Assessment — Old HRIS

These findings describe the Old HRIS state. Their remediation status in the New HRIS is given in Section 10.

FindingSeverityDescription & exploitEvidence
PDS save endpoints — no backend authorization High Access control was JavaScript-only; the backend accepted a POST from any authenticated user. An employee could craft a request to edit another employee's PDS, or alter their own userType to escalate privileges. EMPLOYEE_PDS_EDIT_CHANGES.md
Leave mutation endpoints — broken access control High New leave endpoints inherited the same "authenticated-only" model. An employee could self-approve leave (status=APPROVED), inflate credits via /postLeaveAccrual / /addLeaveCardEntry, and delete or modify records by numeric id (IDOR) — directly falsifying the leave-credit ledger. LeaveController (pre-b10c18b)
Leave Form 6 PDF — IDOR / PII exposure Medium /leaveForm6Pdf/{id} took only a numeric id with no ownership check, so any authenticated user could enumerate ids and download any employee's CS Form 6 (name, position, salary, leave reasons). LeaveController (pre-b10c18b)
Uniform default password across accounts Medium Accounts were provisioned with a shared default password; without forced rotation, accounts are trivially guessable. credentials list
Cross-module authorization pattern Medium The "authenticated is enough" pattern spanned appointments, clearance and 201-file modules — the same class of exposure beyond PDS and leave. controller review
Root cause. The Old HRIS conflated authentication ("who are you") with authorization ("what may you do"). Because the UI hid controls, server-side checks were never added — so the security boundary lived only in the browser, where a user fully controls the requests.

Section 12

Conclusion and Recommendations

Conclusion

The New HRIS is a clear improvement over the Old HRIS on both capability and security. It adds a complete, procedure-aligned Leave Management module and closes the two highest-impact access-control exposures that existed in the Old HRIS. The build is deployable (Java 11, Spring Boot 2.2.4, ~92 MB WAR) and the database migrations are additive and reversible-by-backup.

Deployment verdict: GO for the leave release. The leave module and its authorization fix are ready to deploy, provided the migration-then-WAR order in Section 6.4 is followed and a database backup is taken first.
